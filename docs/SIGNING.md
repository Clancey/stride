# Signing

Stride updates itself over the air. Android will only accept an update signed with the **same key**
as the installed copy, so one key controls whether every console in the field can ever be updated
again. That gives two permanent failure modes, pulling in opposite directions:

| | Consequence |
|---|---|
| **Lose the key** | No console can ever be updated again. Recovery is uninstall + reinstall — on a machine that may be in someone's basement, behind a launcher that is the only UI it has. |
| **Leak the key** | Anyone can sign an APK that every Stride console accepts as a genuine update. There is no revocation, no kill switch, no Play Store to pull it. |

So the key is committed to this repo — but only ever as ciphertext.

## What is in the repo

| Path | Committed? | What it is |
|---|---|---|
| `keystore/stride-release.jks.enc` | **yes** | The signing key, AES-256 encrypted (PBKDF2, 600k iterations). |
| `keystore/stride-release.jks` | no, gitignored | The decrypted key. Exists only between `unlock` and `lock`. |
| `apps/spikes/android/key.properties` | no, gitignored | Generated by `unlock`; contains the passphrase in plaintext. |
| the passphrase | **never** | macOS login keychain + your password manager. |

Committing the ciphertext is the point: it survives a dead laptop, it is versioned, and it is always
where you'd look for it. Committing the *passphrase* anywhere in git would undo all of that, which is
why `unlock` writes `key.properties` rather than the repo carrying it.

## The key

```
alias   stride
algo    RSA 4096, SHA384withRSA
valid   2026-08-14 → 2056-08-06 (30 years)
SHA-256 92:53:4D:3C:0C:F8:14:E0:27:B8:33:8E:A4:CF:DA:0F:54:AD:C5:D5:EF:F3:4D:33:46:35:26:F5:72:88:7E:59
```

That fingerprint is what `signerSha256` pins in `catalog.json`. A console checks the downloaded APK's
certificate against it *before* opening an installer session, so a swapped artifact fails closed even
if the hosting is compromised.

## Building a release

```bash
tools/keystore.sh unlock          # .enc -> .jks + key.properties
cd apps/spikes && flutter build apk --release
tools/keystore.sh lock            # re-encrypt, delete the plaintext
```

`lock` verifies the ciphertext round-trips *before* deleting the plaintext — encrypting to a corrupt
file and then removing the only good copy is exactly the "lose the key" failure above.

Without `unlock`, a release build falls back to the **debug** key so a fresh clone and CI still work.
That fallback is convenient and dangerous in equal measure: a debug-signed APK installs fine and looks
normal, but no console signed with the release key will ever accept it as an update. Before
publishing, confirm what you actually built:

```bash
apksigner verify --print-certs build/app/outputs/flutter-apk/app-release.apk
```

`tools/publish.sh` records whatever signer it finds into the catalog, so it will happily publish a
debug-signed build. Check the fingerprint, not the file's timestamp.

## Builds you hand to someone else

**Every APK that leaves your machine must be signed with the release key — no exceptions.** This is
not a tidiness rule. Stride self-updates, and Android refuses an update signed by a different key
than the installed copy. A tester running a debug-signed build cannot ever be updated: they have to
uninstall first, which wipes their profiles, pins, and goal history. There is no recovery that keeps
their data, and you will not find out until the day you ship a fix.

So: `tools/keystore.sh unlock` before you build anything for anyone, or take the build straight from
the release workflow, which asserts the fingerprint and fails the run if it does not match. Local
debug builds are fine for your own console as long as you accept the same uninstall when you switch
it back.

## Recovering the passphrase

```bash
security find-generic-password -a stride-release -s stride-release-keystore -w
```

If that returns nothing, use the copy in your password manager. If both are gone, the key is gone —
see the first table.

## Rotating

Only if the key leaks, because rotation breaks the update path for every installed console (they must
uninstall and reinstall). Generate a new keystore, `lock` it, publish a new build with a bumped
`versionCode`, and tell anyone running Stride that they need a manual reinstall. There is no way to
make an already-installed console accept a differently-signed update.
